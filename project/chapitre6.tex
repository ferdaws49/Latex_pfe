\subsection{L'architecture BI}
L'architecture de Business Intelligence (BI) est conçue pour collecter, transformer, stocker et analyser les données afin de fournir des informations exploitables aux différents utilisateurs. Elle repose sur un processus structuré garantissant la qualité et la pertinence des données.

\begin{itemize}[label=\textbullet]
\item \textbf{Sources des Données:} Nous distinguons deux modes d'alimentation pour couvrir l'ensemble des besoins du centre:

\begin{itemize}[label=$\star$]
\item \textbf{Intégration Direct:} Synchronisation directe avec les bases opérationnelles pour récupérer en temps réel les données métiers.
\item \textbf{Import Manuel:} Import de fichiers par l'Administrateur pour intégrer l'historique ou des données externes.
\end{itemize}

\item \textbf{Le processus ETL:} Le processus ETL (Extract, Transform, Load) est le cœur de l'architecture BI. Il assure le mouvement et la préparation des données depuis les systèmes sources jusqu'à l'entrepôt de données (Data Warehouse).

\begin{itemize}[label=$\star$]
\item \textbf{Extraction:} Cette phase consiste à récupérer les données brutes provenant des deux sources citées précédemment.
\item \textbf{Transformation:} Une fois extraites, les données sont nettoyées, standardisées, enrichies et agrégées. Cette étape est cruciale pour assurer la qualité et la cohérence des données. Les opérations typiques incluent la suppression des doublons, la correction des erreurs, la conversion des formats, le calcul de nouvelles métriques et l'intégration de données provenant de sources différentes. La transformation prépare les données pour l'analyse et la visualisation, en les rendant conformes aux modèles de données cibles.
\item \textbf{Chargement:} La dernière étape consiste à charger les données transformées dans la destination finale, entrepôt de données (Data Warehouse). Le Data Warehouse est optimisé pour les requêtes analytiques et le reporting, offrant une vue historique et consolidée des informations.
\end{itemize}


\textbf{Architecture en Schéma en Étoile (Star Schema)}

Le cœur de notre modélisation repose sur un \textbf{Schéma en Étoile} comme illustré dans la figure \ref{fig:star_schema}. Cette structure est ainsi nommée car elle organise les données de manière centrale et rayonnante:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{project/images/starschema.png}
    \caption{Schéma en Étoile}
    \label{fig:star_schema}
\end{figure}

\begin{itemize}[label=\textbullet]
\item \textbf{Le centre de l'étoile:} Il est constitué par la \textbf{Table de Faits} (\textit{fact\_finance}). Elle contient les données quantitatives et les clés étrangères. C'est ici que sont stockées les mesures de performance.
\item \textbf{Les branches de l'étoile:} Elles sont représentées par les \textbf{Tables de Dimensions}. Chaque branche fournit un contexte spécifique aux mesures centrales. 
\end{itemize}

L'avantage majeur de cette architecture est la \textbf{dénormalisation contrôlée}. Contrairement à une base transactionnelle classique qui multiplie les jointures, le schéma en étoile simplifie les chemins d'accès aux données, garantissant ainsi des temps de réponse optimaux pour les rapports analytiques.

\textbf{Les Tables de Dimensions}

Les dimensions constituent les axes d’analyse. Elles permettent de "découper" les chiffres selon différents contextes métier: 

\begin{itemize}[label=\textbullet]
    \item \textbf{Dimension Temps (dim\_temps):} Axe temporel indispensable permettant de suivre l'évolution des indicateurs par jour, mois, trimestre ou année.
    \item \textbf{Dimension Formation (dim\_formation):} Regroupe les informations sur les cours (titre, catégorie, statut) pour analyser la rentabilité par thématique.
    \item \textbf{Dimension Session (dim\_session):} Détaille le cadre de réalisation (type, capacité), permettant d'évaluer l'efficacité de l'organisation.
    \item \textbf{Dimension Formateur (dim\_formateur):} Identifie l'intervenant pour analyser l'impact des coûts d'animation sur la marge brute.
    \item \textbf{Dimension Apprenant (dim\_apprenant):} Permet de segmenter les résultats par client et d'analyser les comportements de paiement.
    \item \textbf{Dimension Type Finance (dim\_type\_finance):} Définit la nature du flux (paiement, dépense, remboursement) pour une classification précise.
\end{itemize}

\textbf{La Table de Faits: fact\_finance}

La table de faits enregistre les événements quantitatifs liés à l'activité financière.

\textbf{Les indicateurs (KPIs) stockés sont:}
\begin{itemize}[label=$\star$]
    \item \textbf{Montant:} Flux financier réel enregistré (Cash-flow).
    \item \textbf{CA Théorique:} Revenu potentiel calculé (Prix $\times$ Nombre d'inscrits).
    \item \textbf{Coûts (Formateur et Logistique):} Valeurs permettant de calculer la rentabilité nette par session.
    \item \textbf{Nombre d’inscrits:} Mesure du volume d'activité et du taux de remplissage.
    \item \textbf{Indicateurs Booléens:} Champs (\textit{est\_paiement, est\_impaye}) facilitant la segmentation rapide des données.
\end{itemize}

\textbf{Liaison et Clés Techniques:} La liaison entre le centre (le fait) et les branches (les dimensions) s'effectue via des clés techniques générées (\textit{sk\_temps, sk\_session}, etc.). Cette méthode assure l'intégrité du référentiel analytique indépendamment des évolutions de la base de données de production.ccélère la génération des graphiques dans le dashboard final.

\item \textbf{Restitution et Analyse}
\begin{itemize}[label=$\star$]
\item \textbf{Dashboards Interactifs:} Visualisation sous forme de graphiques (secteurs, barres, courbes) pour identifier les tendances en un coup d'œil.
\item\textbf{Analyses Approfondies:} Grâce aux filtres et au "Drill-down", l'utilisateur peut passer d'une vue globale à une vue détaillée.
\item \textbf{Aide à la Décision:} Le résultat final n'est pas seulement une image, mais un outil permettant de prendre des décisions stratégiques.
\end{itemize}
\end{itemize}

\textbf{Données insuffisantes:} Si l'historique d'un apprenant ou des inscriptions est trop fragmentaire (moins de 3 mois), le système affiche un avertissement et exclut l'élément concerné du calcul prédictif.

\textbf{Indisponibilité du moteur prédictif:} Si le service de calcul IA est inaccessible, le système bascule sur une méthode de secours locale (règles métier pondérées pour l'abandon, projection linéaire pour les inscriptions, indicateurs réels pour les recommandations) tout en signalant à l'utilisateur le mode de dégradation contrôlée.

\textbf{Paramètres invalides:} Si l'utilisateur sélectionne une période de prévision non supportée ou antérieure à la date du jour, le système affiche une erreur de validation et bloque le traitement.

\textbf{Données désynchronisées:} Si les indicateurs des autres modules ne sont pas à jour, le système signale la date de dernière mise à jour et avertit que les recommandations peuvent être obsolètes.

\textbf{Défaillance d'un composant:} Si un widget graphique ou le service de conseils est indisponible, le système affiche un message informatif dans la zone concernée sans bloquer le reste de la page.

\subsection{L'intégration de modéle ML}
Cette section détaille le processus d'intégration des modèles d'apprentissage automatique, en mettant l'accent sur le choix des algorithmes de régression linéaire et logistique, leur justification, et les étapes d'implémentation.

\subsubsection{Type du modèle utilisé}
Le module prédictif repose sur le paradigme de \textbf{l'apprentissage supervisé (Supervised Learning)}. Ce choix méthodologique est dicté par la nature de notre base de données: nous disposons de données historiques annotées (par exemple des historiques de paiements, les résultats obtenus par les apprenants, etc) qui constituent une "vérité terrain".
L'objectif est d'entraîner nos algorithmes à généraliser la relation entre les caractéristiques d'entrée et la variable cible, permettant ainsi de formuler des prédictions précises sur de nouvelles données.

Le choix de ces modèles par rapport à des modèles non-linéaires plus sophistiqués (comme les SVM ou le Deep Learning) s'appuie sur trois piliers fondamentaux:

\textbf{Interprétabilité et Transparence:} L'un des défis majeurs des modèles complexes est l'opacité de leur processus de décision. À l'inverse, les modèles de régression offrent une interprétabilité intrinsèque exceptionnelle.

\textbf{Robustesse face au Surapprentissage:} La complexité d'un modèle est souvent une arme à double tranchant. Les modèles très flexibles ont tendance à mémoriser le bruit présent dans les données d'entraînement (surapprentissage), ce qui dégrade leurs performances sur de nouvelles données.

\textbf{Performance et Rapidité:} Les algorithmes de régression sont simples et consomment très peu de ressources techniques (mémoire, puissance de calcul). Ils sont beaucoup plus rapides à entraîner que des modèles complexes comme le Deep Learning.


\begin{itemize}[label=\textbullet]
    \item \textbf{Pour la prévision du chiffre d’affaires:} Pour cette prévision, nous avons choisi la régression linéaire afin de prédire le chiffre d’affaires, car il s’agit d’une variable quantitative continue. Ce modèle est idéal pour établir une relation directe entre le chiffre d’affaires et les facteurs qui l’influencent, tels que les coûts ou le nombre de participations. Sa simplicité permet d’identifier clairement les tendances, offrant ainsi une prévision chiffrée précise et facile à interpréter pour la direction.
    \item \textbf{Pour la prévision des inscriptions mensuelles:} Pour cette prévision, nous avons opté pour le modèle Meta Prophet, reconnu pour sa performance dans l’analyse des séries temporelles. Ce modèle permet d’estimer l’évolution future des inscriptions sur une période de trois mois en se basant sur les données historiques. Grâce à ces prévisions, le directeur peut anticiper la demande, mieux planifier les ressources disponibles et prendre des décisions stratégiques afin d’optimiser la gestion du centre de formation.
    \item \textbf{Pour la prédiction de l'abandon (Alerts IA) :} 
    L'abandon est un phénomène binaire (un apprenant abandonne ou 
    ne le fait pas), ce qui correspond parfaitement à la nature de 
    la classification supervisée. Deux algorithmes sont candidats : 
    la \textbf{régression logistique}, privilégiée pour son 
    interprétabilité et sa probabilité calibrée, et le 
    \textbf{Random Forest}, choisi pour sa capacité à capturer les 
    interactions non linéaires entre les caractéristiques 
    comportementales (présence, notes, satisfaction, paiement). 
    En analysant ces comportements passés, les deux modèles 
    estiment la probabilité d'abandon. Une procédure de sélection 
    automatique compare leurs performances via l'AUC-ROC sur un 
    jeu de validation ; le modèle le plus performant est retenu 
    pour la production, permettant ainsi au responsable 
    pédagogique d'intervenir de manière proactive auprès des 
    apprenants à risque.
    \item \textbf{Pour la prédiction des sessions déficitaires:} Pour cette prédiction, nous avons utilisé la régression logistique car l'objectif ici est de répondre à une question binaire: la session sera-t-elle déficitaire ou non (Oui/Non) ? Contrairement à la régression classique, ce modèle est spécifiquement conçu pour la classification. Il permet de calculer la probabilité qu'une session tombe en déficit en fonction de certaines variables, ce qui en fait un outil parfait pour l'analyse des risques et l'anticipation des pertes.
\end{itemize}

\subsubsection{Choix des paramètres}
 Cette section détaille l'ensemble des choix techniques et méthodologiques qui structurent notre solution, depuis la sélection des sources de données dans le Data Warehouse jusqu'à la mise en œuvre du processus de prédiction en temps réel


% ─────────────────────────────────────────────────────────────────
% 1. RISK MODEL — ABANDON
% ─────────────────────────────────────────────────────────────────
\textbf{Pour la prédiction du risque d'abandon (Alerts IA) :}

\textbf{Tables utilisées :} Les données sont extraites des tables 
opérationnelles PostgreSQL : \texttt{apprenants}, \texttt{users}, 
\texttt{presences}, \texttt{performance}, \texttt{satisfaction}, 
\texttt{finances} et \texttt{sessions\_apprenants}.

\textbf{Pourquoi ces tables ?} La base relationnelle constitue la source 
de vérité unique. L'absence d'une colonne \textit{abandon} impose la 
construction d'un label proxy basé sur les comportements observés.

\textbf{Attributs clés :}
\begin{itemize}[label=\textbullet]
    \item \textbf{taux\_presence} : ratio de présences validées sur le 
    nombre total de sessions ;
    \item \textbf{absences\_consecutives} : longueur maximale d'une 
    séquence d'absences consécutives ;
    \item \textbf{moyenne\_notes} : moyenne des évaluations (0--20) ;
    \item \textbf{tendance\_notes} : écart entre la dernière et la 
    première note enregistrée ;
    \item \textbf{moyenne\_satisfaction} : moyenne sur échelle 1--5 ;
    \item \textbf{jours\_retard\_paiement} : ancienneté du dernier impayé.
\end{itemize}

\textbf{Détails du modèle :}

\begin{itemize}[label=\textbullet]

    \item \textbf{Construction du label (\texttt{generate\_label}) :} 
    Cette étape génère la variable cible binaire à partir des features 
    comportementales, en évitant l'apprentissage trivial des règles 
    métier fixes.

    \textbf{Processus :}
    \begin{enumerate}
    \item Calcul d'un score de risque $r$ par combinaison pondérée 
    des features, où le taux de présence et la moyenne des notes 
    reçoivent les poids les plus élevés car ils sont les indicateurs 
    les plus prédictifs du décrochage :
   \begin{center}
    \vspace{-0.3cm}
    $\displaystyle
    r = 0.45(1 - \text{taux\_p}) + 0.35\left(1 - 
    \frac{\text{moyenne\_n}}{20}\right) + 
    0.15\left(\frac{\text{jours\_r}}{90}\right) + 
    0.05\left(\frac{\text{absences\_c}}{5}\right)
    $
    \vspace{-0.3cm}
    \end{center}
    \vspace{0.2cm}
        \item Transformation du score $r$ en probabilité via la fonction 
        sigmoïde, ce qui permet de contraindre la sortie dans l'intervalle 
        $[0,1]$ et d'amplifier les différences autour du seuil de 
        basculement $0.45$ :
        \[
        p = \frac{1}{1 + e^{-8(r - 0.45)}}
        \]
        \item Tirage binomial $y \sim \mathcal{B}(1, p)$ : un même profil 
        peut ainsi générer $y=0$ ou $y=1$ selon la probabilité calculée, 
        ce qui force le modèle à apprendre des patterns statistiques 
        plutôt que des règles déterministes.
    \end{enumerate}
    \textit{Résultat :} Un DataFrame enrichi d'une colonne 
    \texttt{abandon} binaire (0 / 1) avec une distribution équilibrée 
    entre les deux classes.

    \item \textbf{Entraînement du modèle (\texttt{train\_risk\_model}) :} 
    Cette étape prépare les données, entraîne les modèles candidats et 
    sélectionne le meilleur selon une métrique adaptée au contexte métier.

    \textbf{Processus :}
    \begin{enumerate}
        \item Séparation des variables explicatives ($X$) correspondant 
        aux 6 features comportementales, et de la variable cible ($y$) 
        représentant le label d'abandon binaire.
        \item Imputation des valeurs manquantes via \texttt{SimpleImputer} 
        avec la stratégie moyenne, indispensable car certains apprenants 
        peuvent ne pas avoir de notes ou de données financières 
        enregistrées. Suivi d'une normalisation via \texttt{StandardScaler} 
        pour homogénéiser les échelles très différentes entre features 
        (taux de présence dans $[0,1]$ vs jours de retard dans $[0,90]$).
        \item Division stratifiée 80/20 sur $y$ afin de préserver la 
        proportion des classes dans les deux ensembles et garantir une 
        évaluation représentative sur le jeu de test.
        \item Entraînement de deux modèles candidats : la Régression 
        Logistique et la Forêt Aléatoire, tous deux configurés avec 
        \texttt{class\_weight='balanced'} pour compenser un éventuel 
        déséquilibre entre apprenants stables et apprenants à risque.
        \item Évaluation sur le jeu de test via l'accuracy, l'AUC-ROC, 
        le F1-score et la matrice de confusion. L'AUC-ROC est retenu 
        comme critère de sélection principal car il mesure la capacité 
        de discrimination indépendamment du seuil choisi, ce qui est 
        essentiel dans un contexte de classes potentiellement 
        déséquilibrées.
        \item Sauvegarde du modèle retenu, du scaler et de l'imputer 
        dans un fichier \texttt{.pkl} pour éviter un réentraînement 
        systématique à chaque requête.
    \end{enumerate}
    \textit{Résultat :} Un modèle entraîné et sélectionné avec ses 
    statistiques d'évaluation complètes.

    \item \textbf{Prédiction (\texttt{predict\_risk}) :} Cette étape 
    calcule le score de risque en temps réel pour chaque apprenant 
    à partir du modèle pré-entraîné.

    \textbf{Processus :}
    \begin{enumerate}
        \item Chargement du modèle, du scaler et de l'imputer depuis 
        le fichier \texttt{.pkl}, ce qui garantit des temps de réponse 
        optimaux sans réentraînement à chaque requête.
        \item Préparation des features du nouvel apprenant : imputation 
        des valeurs manquantes et normalisation selon les paramètres 
        appris lors de l'entraînement, garantissant la cohérence avec 
        le pipeline d'entraînement.
        \item Calcul de la probabilité $p \in [0,1]$ par le modèle, 
        convertie en score de risque entre 0 et 100, puis classée 
        automatiquement en quatre niveaux d'alerte : critique 
        ($\geq 75$), élevé ($\geq 55$), modéré ($\geq 35$), faible.
    \end{enumerate}
    \textit{Résultat :} Un score de risque et un niveau d'alerte 
    associé pour chaque apprenant, transmis au tableau de bord 
    pédagogique.

\end{itemize}

\textbf{Pour la prévision des inscriptions mensuelles :}
 
\textbf{Pour la prévision des inscriptions mensuelles :}

\textbf{Tables utilisées :} \texttt{sessions\_apprenants} et 
\texttt{sessions}.

\textbf{Pourquoi ces tables ?} Ces deux tables constituent la source 
directe des inscriptions effectives : \texttt{sessions\_apprenants} 
enregistre les associations entre apprenants et sessions, tandis que 
\texttt{sessions} fournit les dates nécessaires à l'agrégation mensuelle.

\textbf{Attributs clés :}
\begin{itemize}[label=\textbullet]
    \item \textbf{ds} : mois au format \texttt{YYYY-MM}, constituant 
    l'axe temporel de la série ;
    \item \textbf{y} : nombre d'inscriptions effectives agrégées 
    pour chaque mois.
\end{itemize}

\textbf{Détails du modèle :}

\begin{itemize}[label=\textbullet]

    \item \textbf{Chargement des données 
    (\texttt{load\_inscriptions\_data}) :} Cette étape agrège 
    les inscriptions mensuelles et prépare la série temporelle 
    pour l'entraînement.

    \textbf{Processus :}
    \begin{enumerate}
        \item Agrégation mensuelle des inscriptions effectives 
        en joignant \texttt{sessions\_apprenants} et 
        \texttt{sessions}, regroupées par mois via la fonction 
        \texttt{TO\_CHAR}. Un minimum de 3 mois d'historique 
        est requis pour garantir une modélisation valide.
        \item Le DataFrame résultant suit la convention Prophet 
        avec une colonne \texttt{ds} (date) et une colonne 
        \texttt{y} (effectif mensuel), convertie en 
        \texttt{float} pour assurer la compatibilité des 
        deux modèles candidats.
        \item Application d'une moyenne mobile d'ordre 3 sur 
        la colonne \texttt{y} afin de réduire le bruit mensuel 
        lié aux sessions intensives ponctuelles, tout en 
        préservant les tendances de fond.
        \item Exclusion du dernier mois si celui-ci compte 
        moins de 20 jours écoulés, afin d'éviter un biais 
        de sous-estimation dû à des données incomplètes.
    \end{enumerate}
    \textit{Résultat :} Une série temporelle mensuelle lissée, 
    prête à être utilisée par les deux modèles candidats.

    \item \textbf{Entraînement et sélection du modèle 
    (\texttt{train\_forecast\_model}) :} Cette étape compare 
    deux approches complémentaires sur un split chronologique 
    rigoureux et retient la plus performante selon le MAE.

    \textbf{Processus :}
    \begin{enumerate}
        \item Division chronologique 80/20 du jeu de données, 
        en respectant strictement l'ordre temporel pour éviter 
        toute fuite de données du futur vers le passé 
        (\textit{data leakage}), condition indispensable pour 
        la validité d'une modélisation par séries temporelles.
        \item Entraînement de deux modèles candidats sur 
        l'ensemble d'entraînement :
        \begin{itemize}[label=\textbullet]
            \item \textit{LinearTrend} : régression linéaire 
            sur l'indice temporel $t = 0, 1, 2, \ldots$, 
            servant de modèle de référence robuste et 
            interprétable, garantissant la continuité du 
            service même en cas de données insuffisantes ;
            \item \textit{Prophet} : modèle additif de séries 
            temporelles avec saisonnalité annuelle activée 
            si l'historique couvre au moins 24 mois, offrant 
            une meilleure gestion implicite des changements 
            de tendance et des intervalles de confiance à 
            $80\%$.
        \end{itemize}
        \item Évaluation des deux modèles sur le jeu de test 
        via le MAE et le RMSE. Le modèle présentant le MAE 
        le plus faible est retenu comme modèle principal, 
        tandis que LinearTrend est systématiquement conservé 
        comme fallback pour garantir la continuité du service.
        \item Sauvegarde du modèle principal et du fallback 
        dans un fichier \texttt{.pkl}, incluant les données 
        d'historique et les métriques d'évaluation.
    \end{enumerate}
    \textit{Résultat :} Un modèle principal sélectionné et 
    un fallback sauvegardés, accompagnés de leurs métriques 
    de performance respectives.

    \item \textbf{Prédiction (\texttt{predict\_forecast}) :} 
    Cette étape génère les prévisions mensuelles futures 
    à partir du modèle pré-entraîné.

    \textbf{Processus :}
    \begin{enumerate}
        \item Chargement du modèle principal depuis le fichier 
        \texttt{.pkl} sans réentraînement, garantissant des 
        temps de réponse optimaux à chaque requête.
        \item Génération des prévisions pour les mois futurs 
        demandés, produisant pour chaque mois une valeur 
        prévue et ses bornes de confiance (\texttt{yhat}, 
        \texttt{yhat\_lower}, \texttt{yhat\_upper}).
        \item Calcul automatique de la tendance globale 
        (hausse / baisse / stable) en comparant le dernier 
        mois observé au premier mois prédit, avec un seuil 
        de $\pm 10\,\%$. En cas d'erreur du modèle principal, 
        le fallback LinearTrend est automatiquement activé 
        pour garantir la continuité du service.
    \end{enumerate}
    \textit{Résultat :} Une liste de prévisions mensuelles 
    datées avec leurs bornes de confiance et la tendance 
    globale détectée.

\end{itemize}


\textbf{Pour la prédiction des sessions déficitaires:}

Les données utilisées pour la prédiction des sessions déficitaires proviennent du Data Warehouse et sont obtenues via des requêtes SQL.
\begin{itemize}[label=\textbullet]
    \item \textbf{dw.dim\_session:} table centrale de la requête, fournissant l'identifiant, la date, la capacité et le type de session.
    \item \textbf{dw.fact\_finance:} source principale des montants financiers.
    \item \textbf{dw.dim\_type\_finance:} permet de séparer paiements, coûts formateur, coûts logistique et impayés.
    \item \textbf{dw.dim\_formation} et \textbf{dw.dim\_formateur:}  utilisées pour les filtres optionnels par formation et par formateur.
\end{itemize}
\textbf{Attributs extraits}

\begin{itemize}[label=\textbullet]
    \item \textbf{session\_id:} identifiant unique de la session
    \item \textbf{nb\_inscrits:} nombre d’inscrits réels
    \item \textbf{capacite:} capacité maximale (doit être $> 0$)
    \item \textbf{revenu:} chiffre d’affaires de la session
    \item \textbf{cout\_formateur:} coût du formateur
    \item \textbf{cout\_logistique:} coût logistique
    \item \textbf{impayes:} montant impayé
    \item \textbf{date:} date au format ISO (YYYY-MM-DD)
\end{itemize}

\textbf{Details du modele}
\begin{enumerate}
    \item Le ML Service reçoit les critères de filtre depuis NestJS (date\_from, date\_to, formation\_id, formateur\_id, session\_type) et traduit ces paramètres en clauses WHERE SQL.
    La requête joint dw.dim\_session (table centrale) à dw.fact\_finance via sk\_session, avec dim\_formation et dim\_formateur pour les filtres optionnels.
    Seules les sessions répondant aux critères sont extraites, nettoyées et transformées en features. Cette approche évite le transfert de données brutes entre NestJS et le ML Service, conformément à l'architecture unifiée des deux pipelines de prédiction.
    \item \textbf{Nettoyage}
    \begin{itemize}[label=\textbullet]
        \item Suppression des identifiants nuls
        \item Conversion des champs numériques
        \item Filtrage des sessions sans capacité ou données financières
    \end{itemize}

    \item \textbf{Feature Engineering} Calcul des features suivantes à partir des données extraites:
    \begin{itemize}[label=\textbullet]
        \item \textbf{fill\_rate:} taux de remplissage (inscrits / capacité)
        \item \textbf{cout\_total:} somme des coûts formateur et logistique
        \item \textbf{marge:} revenu - coût total
        \item \textbf{taux\_impaye:} ratio des impayés
        \item \textbf{month:} mois de la session (saisonnalité)
    \end{itemize}

    \item \textbf{Création des labels} La variable cible is\_deficit est définie comme une indicatrice binaire: 1 si la marge nette est strictement négative, 0 sinon.
    \item \textbf{Vérification des classes} Vérification de la présence des deux classes avec au moins deux échantillons chacune.
    \item \textbf{Séparation Train/Test} Division 80/20 avec un \texttt{test\_size = 0.2} et \texttt{random\_state = 42}. Utilisation de \texttt{stratify=y} pour préserver la proportion des classes déficit/non-déficit dans les deux sous-ensembles, essentiel lors d'un déséquilibre de classes.
    \item \textbf{Normalisation:} Application de \texttt{StandardScaler} ajusté uniquement sur \texttt{X\_train} pour éviter la fuite de données.
    \item \textbf{Entraînement:} Modèle utilisé : Régression Logistique (\texttt{sklearn.linear\_model.LogisticRegression}), un algorithme de classification binaire, avec \texttt{class\_weight = "balanced"} et \texttt{max\_iter = 1000}
    \item \textbf{Évaluation:} Calcul de l'accuracy, du ROC-AUC, de la précision, du recall et du F1-score sur le jeu de test, complété par une matrice de confusion.
    \item \textbf{Persistance:} Sauvegarde du modèle et du scaler avec \texttt{joblib} (session\_deficit\_model.pkl et session\_deficit\_scaler.pkl). Cette persistance évite un réentraînement systématique à chaque redémarrage du serveur.
    \item \textbf{Prédiction:}
    \begin{itemize}[label=\textbullet]
        \item \textbf{Chargement} Le modèle et sa configuration de normalisation sont récupérés.
        \item \textbf{Preparation} Les nouvelles sessions sont nettoyées, transformées en features et normalisées.
        \item \textbf{Scoring} Le modèle estime la probabilité de déficit de chaque session.
        \item \textbf{Decision} Cette probabilité est traduite en trois niveaux: LOW ($\leq 0.5$), MEDIUM ($> 0.5$), HIGH ($> 0.8$).
        \item \textbf{Action} Génère une recommandation basée sur le risque et le taux de remplissage.
    \end{itemize}
\end{enumerate}

\subsubsection{Évaluation des résultats}

\subsection{Recommendations}
Le module de recommandations stratégiques exploite les capacités de l'intelligence artificielle générative pour transformer les indicateurs de performance du centre en conseils opérationnels personnalisés. Il constitue le volet décisionnel du tableau de bord du Directeur, accessible depuis la page « Rapports stratégiques ».

\subsubsection{Principe de fonctionnement}

Contrairement aux modèles prédictifs classiques qui estiment une valeur numérique, ce module produit des analyses textuelles structurées. Le système s'appuie sur un modèle de langage (LLM) afin de générer automatiquement des fiches de recommandations à partir du contexte métier du centre.

Le processus repose sur trois étapes successives :

\begin{enumerate}[leftmargin=*]
    \item \textbf{Agrégation des indicateurs :} Le système collecte les KPI actuels du centre (taux d'abandon, taux de réussite, satisfaction moyenne, revenus, taux de remplissage des sessions) à partir de la base de données décisionnelle.
    
    \item \textbf{Construction du prompt métier :} Les indicateurs sont structurés dans un prompt qui synthétise la situation du centre. Ce prompt sollicite la génération de trois conseils stratégiques distincts, priorisés et actionnables.
    
    \item \textbf{Génération et structuration :} Le modèle de langage traite le prompt et retourne trois recommandations classées selon leur impact (critique, moyen, positif) et leur facilité de mise en œuvre.
\end{enumerate}

\subsubsection{Données d'entrée et format de sortie}

Les données d'entrée correspondent aux indicateurs clés de performance consolidés par le module BI. La sortie se présente sous la forme de trois recommandations structurées, chacune comprenant:
\begin{itemize}[label=$\bullet$,leftmargin=*]
    \item un intitulé décrivant l'action suggérée ;
    \item la catégorie concernée (pédagogique, financière ou organisationnelle) ;
    \item le niveau d'impact estimé ;
    \item les indicateurs ayant motivé la recommandation.
\end{itemize}

\subsubsection{Consultation et exploitation}

Les recommandations générées sont affichées dans la section inférieure de la page « Rapports stratégiques », sous forme de fiches interactives. Le Directeur peut consulter ces conseils stratégiques et les utiliser comme support décisionnel pour orienter ses actions de gestion. À ce stade de l'implémentation, le module se limite à la génération et à la consultation des recommandations, sans mécanisme backend d'acceptation, de validation ou d'archivage.

\subsubsection{Intégration technique et résilience}

Le modèle de langage utilisé (LLaMA 3) est sollicité via une API externe. Afin de garantir la continuité du service en cas d'indisponibilité de cette API, le système intègre un mécanisme de secours local. Ce dernier génère algorithmiquement trois axes de recommandations à partir des mêmes indicateurs réels, assurant ainsi une dégradation contrôlée sans interruption pour le Directeur.
\subsubsection{Validation des recommandations}

Contrairement aux modèles prédictifs numériques (régression, classification) 
où la performance se mesure par des métriques statistiques (MSE, accuracy, F1-score), 
le module de recommandations repose sur un modèle génératif de langage. 
La qualité des conseils produits est évaluée selon deux critères :

\begin{itemize}[label=$\bullet$,leftmargin=*]
    \item \textbf{Cohérence métier :} Les recommandations doivent s'appuyer 
    strictement sur les indicateurs réels fournis en entrée, sans hallucination.
    \item \textbf{Actionnabilité :} Chaque conseil doit être concret, réalisable 
    et classé selon un niveau d'impact pertinent pour le centre de formation.
\end{itemize}
